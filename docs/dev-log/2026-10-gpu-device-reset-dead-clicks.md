# 画廊点了没反应（D3D12 `DEVICE_RESET`）：死设备、空帧、以及恢复

> 现象：`gallery`（D3D12）跑几分钟后窗口**冻住** —— 标题栏还能拖、鼠标还在动，
> 但点什么都没反应。日志里是 `DXGI_ERROR_DEVICE_RESET (0x887A0006)`。

---

## ★ 结论（先看这段）

**「点了没反应」不是输入的问题，是 GPU 死了之后每一帧都返回空帧。**

`HostWindow::frame()` 在设备失效后仍然每帧照常跑 `diff` / `layout`，
只是最后把 `display_list` 丢掉、返回 `empty_frame()` —— 宿主于是
「要不要推上屏」这个判断上没有东西可推。输入同步**一直在跑**，点击也
**一直被处理**，只是画面上什么都不变，所以看起来像「点了没反应」。

设备为什么会死：本轮改动**不是**原因（见下面「排除的假设」）。D3D12 上
设备被移除（TDR、驱动更新、睡眠唤醒）是**既成事实**，宿主必须能从中恢复 ——
以前不能，所以一次 TDR 就把窗口永久冻住。

修法：设备死了就**重建整条 GPU 栈**，限流每秒一次；死了但还没轮到重建时，
事件循环改 `ControlFlow::WaitUntil`，别空转烧 CPU。

门禁：`zephyra-winit-d3d12/tests/device_lost_gate.rs`（6 条，全部不需要真 GPU）。

---

## 现象与排查

症状链是这样连起来的：

1. `Present` 回 `0x887A0006`（`DXGI_ERROR_DEVICE_RESET`）。
2. 宿主记下 `device_dead = true`，此后**每一帧**都跳过绘制，返回空帧。
3. 输入事件照常进 `Gallery::click`，状态照常改，`view()` 照常重建树。
4. 但树画不出来 ⇒ 画面一动不动 ⇒ 人看到的是「点了没反应」。

第 3 步是关键：**点击处理和绘制是两条独立的路**。所以排查时不要从输入下手
—— 输入那一侧从头到尾都是好的。判据很简单：日志里有没有 `DEVICE_RESET`。

### 死设备时宿主在做什么

`frame()` 的返回值在设备死了之后是 `empty_frame()`，而宿主的推进判断是
「这一帧有没有内容」⇒ 永远不推。于是：

- 画面停在设备死掉前的最后一帧（不是黑屏，是**冻结**）；
- 窗口的非客户区（标题栏、边框）由 DWM 画，所以拖得动 —— 这正是最容易
  误导人的地方：「拖得动」让人以为窗口还活着。

## 排除的假设

| 曾经的怀疑 | 排除方式 |
|---|---|
| 「本轮改动（hover/press 视觉、i18n、`glass` 路由）把 quad 数推高，超了预算」 | HEAD 基线 `quads=206`，改后 `quads=242`。242 远不是能让设备重置的量级；且干净检出跑 3 次**同样**会死 |
| 「是某个新控件的 PSO / 描述符用法越界」 | 用 `ZEPHYRA_FORCE_REBUILD` 临时钩子（用完已删）强制每帧重建，仍会死 —— 说明不是某一帧的资源用法 |
| 「是 DComp 路径特有的」 | `ZEPHYRA_DCOMP` 关掉走普通 present，同样会死 |
| 「是 `--dump-cpu` / 无 GPU 路径引入的」 | `--dump-cpu` 走 `CpuHost`，完全不碰 D3D12，与本问题无关 |
| 「windows crate 里能主动触发设备移除来复现」 | `windows 0.62.2` 的 `ID3D12Device` 没有暴露 `SetDeviceRemovedReason`，**无法**在测试里人为制造设备移除 —— 所以门禁只能测「死之后的行为」，测不了「怎么让它死」 |

最后一行解释了为什么这个 dev-log 没有「如何复现」一节：**本机没有可用的
设备移除触发器**。这是已知的测试盲区，不是没查。

## 现在的行为

### 恢复 = 重建，不是修补

`DEVICE_REMOVED` 之后设备对象失效，绑在它上面的**一切**都失效：PSO、
描述符堆、图集纹理、离屏 RT、命令分配器。继续用旧资源只会每帧失败，而且
失败点各不相同（那正是最难查的一类）。所以恢复只能是**重建整条 GPU 栈**：
设备 → 交换链 → DComp 树 → 渲染器。

`HostWindow::rebuild_gpu()` 的两条硬性顺序（源码里各有说明）：

1. **先建新的，全部成功了才替换旧的。** 中途失败直接 `return Err`，此时
   `self` 一个字都没改 —— 下一轮重试的起点是干净的。反过来先拆旧的再建新的，
   一旦中途失败就留下「旧的没了、新的没建起来」的空壳，窗口彻底不显示。
2. **替换顺序按「谁引用谁」**：先放引用方（DComp visual），再放被引用的
   （chain），最后是设备与渲染器 —— 与字段声明顺序相反，因为这是部分重建，
   不是整体析构。

重建完还要把三样东西清掉：保留树（`FrameCache`）、纹理表、图集上传水位
（`atlas_revision_uploaded`）—— 新渲染器的图集是空的，不清就会拿旧水位
当「已经传过了」，症状是**全部文字消失**。

### 限流：每秒最多一次

拖动期间 `frame()` 每秒被叫几十次。不限流就是每秒几十次重建 —— 那比
「画面冻结」更糟。`should_attempt_recovery(elapsed)` 把这条判据单独拎出来
做纯函数，于是它可以被门禁直接断言，不需要真设备。

### 死着的时候别空转

设备死了但还没轮到重建的那一秒，事件循环改成 `ControlFlow::WaitUntil(下次重建时刻)`；
活着时是 `Wait`。这条容易被忽略：死设备时若继续 `Wait`，就是每帧全速空转，
风扇转起来而画面一动不动 —— 用户会以为是死循环。

## 门禁（`tests/device_lost_gate.rs`，6 条，全部不需要真 GPU）

| 测试 | 钉住什么 |
|---|---|
| `never_draws_when_device_is_dead` | 死设备时**一帧都不画**，且每帧清掉屏幕上的旧 visual |
| `resize失败时冻结` | resize 失败时**保持**旧尺寸、旧画面（不是黑屏、不是拉伸） |
| `draws_normally_when_size_unchanged_or_resize_succeeded` | `Same` 是**动态**判断：内存里状态一变就重新判 |
| `truth_table_is_complete` | 真值表穷举 —— 防止以后加新状态时漏判 |
| `recovery_is_rate_limited_to_one_attempt_per_second` | 限流：重建不能每帧都试 |
| `dead_device_never_draws_but_is_still_eligible_for_recovery` | 死设备**不再画**，但**仍然可以恢复** —— 这两件事必须同时成立 |

那条真值表测试是重点：`should_draw_frame(size_state, device_dead)` 的四种组合
全部断言过。加新状态时它会红，而不是靠人记住。

## 方法论教训

**「点了没反应」这类症状，先问「画面上有没有东西在变」。**

如果画面完全静止而输入仍在处理，那么输入侧无论怎么查都是好的 —— 这一轮
差点就在输入同步里翻了半天。判据只要一句话：日志里有没有设备错误。

这一条与 `2026-10-gpu-device-hung.md` 是**同一族**问题的不同两面：那一篇讲
「怎么别把 GPU 拖死」（resize 不重建交换链），这一篇讲「死了以后怎么活过来」。
两篇都指向同一个结论：**先让回码说话**，别靠读码推导成因。
