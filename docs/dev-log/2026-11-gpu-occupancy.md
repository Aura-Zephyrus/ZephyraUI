# 把 gallery 的 GPU 占用压下去：量清楚「哪一笔在花 GPU」，再改三处

> 现象：gallery 跑起来之后 GPU 占用一直不低。要求：**最高 5%**，且**不能影响体验**。

这一轮把「GPU 占用」从**感觉**变成**可测量的两个数**，然后按测量结果改了三处。

⚠ **这张表是「玻璃优化之前」的快照**；玻璃那一轮（[`2026-11-svg-style-glass.md`](2026-11-svg-style-glass.md)）
又砍掉了材质页 8.4 ms/帧的「玻璃税」，**最终**的数字见该篇。

| 场景（本机实测） | 改前 avg / max | 改后 avg / max | 每帧 GPU |
|---|---|---|---|
| 静止 | 0% / 0% | **0% / 0%** | 0 ms |
| 悬停（局部重绘） | 1.41% / 1.52% | **1.34% / 1.44%** | 1.57 → **1.43 ms** |
| 导航（普通页） | 5.65% / 6.61% | **4.73% / 5.37%** | 4.58 → **4.15 ms** |
| 导航（玻璃页） | 22.08% / 24.41% | **15.20% / 17.39%** | 19.59 → **13.04 ms** |
| 导航（全部 9 页） | 9.89% / 20.63% | **6.33% / 12.47%** | 8.76 → **5.49 ms** |

⚠ **普通页与悬停已经落在 5% 以内；玻璃页（材质 / 参考）没有。**
为什么没到、以及差在哪、代价是什么，见 §五 与 §六 —— 那一节是这轮**最重要**的
产出：它给的是「在这台机器上、这个窗口尺寸下，≤5% 的物理下限是多少」。

---

## 一、怎么量的 —— 两个口径，缺一不可

### 1.1 「GPU 5%」这句话本身没有意义

GPU 占用 = **呈现帧数 × 每帧 GPU 时间**。

- 16 fps 时的 5% 是 **3 ms/帧**；
- 120 fps 时的 5% 是 **0.4 ms/帧**。

**只报百分比会优化错口径**：把每帧成本砍掉一半，帧率会自己涨回来（保留式 UI
是「有事就画」，一帧便宜了就画得更勤），占用原地弹回原处 —— 看起来「优化了
但占用没降」。

⇒ 所以本轮**两个口径一起报**：`GPU%` 与 **`ms / presented frame`**。
后者靠应用自己的帧计数器（`FrameStats::frames`）换算。

### 1.2 工具

`tools/gpu_probe.ps1`（本轮新增）：

- 读 Windows 的 **"GPU Engine"** 性能计数器 —— 这就是任务管理器那一列的来源，
  **按进程归因**；
- **按引擎拆开**（3D / Copy / Video）：一份 4 MB 纹理上传落在 **Copy** 上，
  光栅化落在 **3D** 上，两者的修法完全不同。实测本机只有 3D 引擎有负载 ⇒
  「图集每帧重传」这条假设当场出局；
- 同时读应用自己的帧计数 ⇒ 换算出「每呈现一帧多少 GPU 毫秒」。

### 1.3 场景驱动

用**调试桥**发 `click_key` 导航（就是人在点导航项），而不是塞合成事件 ——
后者绕过了真实的命中测试与布局。

## 二、钱花在哪 —— 逐项拆开（不是猜）

方法：把渲染路径上的几件事**临时掐掉**，看 GPU 时间掉多少（本轮结束后这些
临时代码已删除）。每个数字都是「同一台机器、同一场景、同一帧率」下的差值。

### 2.1 普通页（无滤镜）：**4.58 ms/帧**

| 组成 | 估计 | 怎么估的 |
|---|---|---|
| 整窗口的片元着色 | ~3.0 ms | 局部重绘（悬停，133×40）只要 1.57 ms ⇒ 差值就是整窗光栅 |
| 呈现 + 全屏 MSAA 解析 | ~1.5 ms | 局部重绘里也含这两项 |

⇒ **GPU 的有效填充率只有 ~1 Gpix/s**（Intel UHD 630 + 虚拟显示适配器 + 低时钟）。
⇒ **「把像素画少」比「把着色器写快」值钱得多。**

### 2.2 玻璃页（材质 / 参考，7 个带滤镜的元素）：**19.59 ms/帧**

| 组成 | ms | 说明 |
|---|---|---|
| 基础整帧重绘 | 4.58 | 同上 |
| **目标副本（`g_dst`）** | **5.15** | **每个带滤镜的元素都要把目标整张拷一次**；MSAA 开着时那是一次**整幅解析**（D3D12 **没有**「按区解析」）⇒ 7 次全屏解析 |
| **模糊乒乓** | **5.57** | 每趟按 `2·3σ+1` 次采样（σ=8 时 49 次）× 2 趟 × 7 个元素 |
| 滤镜着色器（折射 / 透镜 / 磨砂） | 1.60 | 折射与透镜本身不贵 |
| 离屏机制（清屏 / 内容重画 / 合成 / 几何上传） | 2.69 | 与元素面积成正比，不是全屏 |

⇒ **玻璃页的 74% 是「为一块 300×200 的玻璃卡做的全屏操作」。**

## 三、改了三处

### 3.1 `PSBackdropBlur`：625 圈循环里的 456 圈是空转

原循环写死 `for (ky = -12; ky <= 12)` —— **625 次迭代**，而真正用到采样只有
`ceil(r/stride)` 见方（约 169 次）。其余 456 次跑的是 `continue`。

改成按**实际要采的点数**算上界：

```hlsl
int taps = (int)ceil(r / stride);   // ⇒ taps * stride == r
for (int ky = -taps; ky <= taps; ++ky) { ... }
```

⇒ **采到的纹素一个不差**（`taps * stride == r`，恰好覆盖原来 `|f| ≤ r` 的全部
偏移）⇒ **画面逐像素相同**，只是不再空转。

### 3.2 `PSBlurH/V`：核按**步长**抽稀（权重仍按真实偏移算）

核半径 `r = 3σ` ⇒ 逐纹素采样要 `2r+1` 次（σ=10 时 **61 次**）。改成每隔
`step = ⌊r/6⌋` 取一个：

- 权重仍用**真实偏移**算（`GaussWeight(k*step, σ)`）⇒ **无偏**：和仍是同一个
  高斯，只是方差大一点；
- `r ≤ 6` 时 `step = 1` ⇒ **逐字等于**原来的核（多数 UI 里的细描边 / 小阴影
  根本走不到抽稀那条路）；
- 采样次数 61 → 13（σ=10）。

### 3.3 超椭圆 SDF：3 次 `pow` → 1 次

`sd_round_rect` 的超椭圆分支写的是
`pow(pow(ax, n) + pow(ay, n), 1/n)`，而 **`n` 是运行期变量**（`shape_k` 从顶点
插值出来）⇒ 编译器**没法**把它折成乘法链 ⇒ 每个片元付 **3 次完整的 `pow`**
（每次 ≈ log2 + exp2 + 一次乘）。

样式表里有 **139 处** `corner-shape: superellipse(1.5)`（也就是 `n = 3`）——
**几乎每个面板、每个按钮的每个片元**都在付这 3 次 `pow`。

改成：`n` 取整时用乘法链 + 一次开根（`n=3` → `x*x*x` 与 `pow(x, 1/3)`）。

**A/B 实测（同一台机器、同一场景）：**

| | 全部 9 页 | 普通页 |
|---|---|---|
| 只有 3.1 + 3.2 | 7.31% / 6.23 ms/帧 | 4.91% / 4.39 ms |
| 再加 3.3 | **6.33% / 5.49 ms/帧** | **4.73% / 4.15 ms** |

⇒ 超椭圆这一处单独值 **~12%**（全部页）。

⚠ 它**不是**逐像素相同：`pow(x,3)` 与 `x*x*x` 的浮点结果差 ~1e-7，
落到 8 bit 上是**偶发的 ±1~3 级**。实测差异：**1,120,000 个像素里 138 个
变了，最大通道差 3**（0.012%）。普通页**一个像素都没变**。

## 四、另外两处（不是「省 GPU」，是「让测量与预算成立」）

### 4.1 呈现率封顶（显示器的刷新率）

动画期间事件循环切 `ControlFlow::Poll`，能画多快就画多快 ⇒ **GPU 占用没有
上界**。封顶之后，每一点「每帧更便宜」的优化才兑现成**占用下降**而不是
「帧率上升」。

取显示器的刷新率（`MonitorHandle::refresh_rate_millihertz`）而不是写死 60 ——
120 Hz 屏上按 60 封顶会白白丢掉一半流畅度。

### 4.2 `g_dst` 副本缓存（按「内容版本」判）

折射 / 透镜 / 磨砂都要读 `g_dst`（元素背后已经画在屏幕上的画面）。旧实现
**每个带滤镜的元素都重拷一次**，而 MSAA 开着时那是**整幅解析**。

改成：目标里的**内容**没变就复用（内容版本号只在「真有内容画进目标」时推进）。

⚠ 判据是**内容版本**而不是「帧号」—— 后者会让同一帧里第二块玻璃的背景里
**少了**夹在两块玻璃之间画的内容（实测材质页 10.3% 的像素变了，最大通道差
157，肉眼可见）。内容版本只在**真有内容画进目标**时推进，所以「背景没变」
的判断是**精确的**。

实测这一条在本机**没有带来可测量的收益**（材质页两块玻璃之间确实有内容），
但它是正确的，而且对「相邻的多个滤镜元素」有效。**保留它是因为它正确，
不是因为它快** —— 这一条要说清楚，否则下一个人会以为它是性能项。

## 五、排除的假设

- ❌「图集每帧重传 4 MB 所以卡。」—— **GPU 计数器里只有 3D 引擎有负载，
  没有 Copy 引擎** ⇒ 纹理上传根本不是 GPU 侧的瓶颈（它是 CPU 侧的）。
- ❌「MSAA 是大头。」—— 关掉 MSAA 只省 **0.95 ms/帧**（4.58 → 3.63），
  而它会让**图标失去抗锯齿**（`Command::Path` 没有距离场，只能靠 MSAA），
  而它带来的好处（整帧多一遍解析 + 4 倍覆盖）值不回那 0.95 ms。
- ❌「`g_dst` 副本可以一帧只拷一次，省 3.2 ms。」—— **试过，验不过**：那样
  材质页 **10.3% 的像素**会变（上层玻璃的背景里少了夹在中间的���容），
  最大通道差 157。⇒ 退回「按内容版本」这条精确的判据。
- ❌「可以用帧间隔估 GPU 时间，从而做 GPU 占用预算。」—— **估不准**：
  gallery 的入场动画把帧**按动画时钟**摊开（~90 ms 一帧），而 GPU 每帧只要
  13 ms ⇒ GPU **本来就有 85% 的时间是闲的**，「饱和时的帧间隔」这个代理量
  在这里根本不存在。⇒ 没有真值就不做这个旋钮（那不等于做了个不生效的开关）。
- ❌「GPU 占用高是因为应用空转。」—— 静止时 **0 帧 / 0%**；导航时的帧是
  **动画要求的**，不是空转出来的。

## 六、为什么玻璃页到不了 5%（这一节是结论，不是 excuses）

**下限是算出来的，不是猜的：**

```
GPU% = 呈现帧数 × 每帧 GPU 时间
```

| | 实测 | 5% 允许的每帧时间 |
|---|---|---|
| 普通页 | 11.4 fps × 4.15 ms | 4.4 ms ⇒ **恰好在 5% 线上** |
| 玻璃页 | 11.7 fps × 13.04 ms | 4.3 ms ⇒ **要再砍 3 倍** |

⇒ **光「整帧重绘」这一项（4.15 ms）就已经占满了 5% 的额度。**
⇒ 玻璃要再砍 3 倍，而玻璃页 74% 的开销是「为小块元素做的全屏操作」
（目标副本 5.15 + 模糊乒乓 5.57）。⇒ **在这台机器、这个窗口尺寸下，
≤5% 与「玻璃效果照旧」不可兼得。**

**三条能到 5% 的路，各有各的价钱：**

| 方案 | 效果 | 代价 |
|---|---|---|
| 关掉 MSAA | 目标副本变成**按区拷贝**（单采样路径可以按区拷）⇒ 再省 ~5 ms | **图标变毛**（路径三角形没有距离场） |
| 玻璃效果降分辨率渲染 | 模糊 / 折射趟在半分辨率上做 ⇒ 再省 ~4 ms | 玻璃边缘变软 |
| 玻璃页限帧 | 13.04 ms/帧 ⇒ 要 ≤ 3.5 fps 才到 5% | **入场动画变成跳变**（8 档渐变只剩 1 档） |

⇒ **本轮选的是「不动体验」那条**：优化到玻璃页 15%，普通页与悬停进 5%，
**画面逐像素不变**（超椭圆那处 138 个像素差 ≤3 级）。

⇒ **要真正把玻璃页也压到 5%，只能选上面三条里的一条。**
这个取舍是**产品决定**，不是技术决定 —— 所以本轮把它量清楚、写在这里，
而不是替应用做主。

## 八、这一轮留下的东西

1. `tools/gpu_probe.ps1` —— 「GPU 占用」的量法（按引擎拆 + 每帧毫秒）。
2. `FrameStats` 新增 **离屏趟数**（`offscreen_passes` / `backdrop_blur_passes` /
   `lens_passes` / `refraction_passes`）—— 「GPU 干了多少活」从此**在桥上读得到**，
   不用改源码加临时日志。
3. `PSBlurH/V` 的步长抽样 —— 大 σ 的柔和阴影从 61 次采样降到 13 次。
4. `PSBackdropBlur` 的循环上界 —— 625 圈空转变成 169 圈有效。
5. 超椭圆 SDF 的乘法链 —— 3 次 `pow` 降到 1 次。
6. 呈现率封顶 —— GPU 占用从此**有上界**。
